# Thread-attention specification

## 포착 모델

- Hermes가 만들거나 참여한 Discord 쓰레드는 사용자의 방문이나 제어 명령 없이
  자동으로 쓰레드 인벤토리에 등록한다.
- 라이브 쓰레드 이벤트, Hermes의 영속 참여 기록, 허용된 채널의 복구 열거 결과를
  사용해 재시작과 Discord 자동 보관 뒤에도 인벤토리를 복구할 수 있어야 한다.
- 인벤토리의 논리 키는 `(scope_id, thread_id)`다. 서버 범위, 부모 채널과 쓰레드
  식별자, 발견 시각, 마지막 Hermes 활동 시각, 마지막 Discord 활동 시각, 실제
  자동 보관 기간, 예상 자동 보관 시각, 관찰된 사용자 상호작용 시각, 확인 기준점,
  종료 상태, 등록 출처, 과거 가져오기 여부, 링크 가능 상태와 확인 시각, 자동 발견
  기준 시각, 마지막 노출 시각, 갱신 시각을 저장할 수 있어야 한다.
- Discord가 제공하지 않는 사용자의 단순 열람 여부는 저장하거나 추정 사실처럼
  표시하지 않는다. 사용자 메시지와 향후 명시적 확인을 관찰 가능한 대용 신호로
  사용한다.

## 최초 과거 가져오기

기능을 현재 Hermes 프로필에서 처음 켤 때, Hermes의 영속 참여 기록에 남아 있는
기존 쓰레드를 기간 제한 없이 모두 쓰레드 인벤토리에 등록한다.

- 최초 가져오기 시작 전에 이미 존재하던 항목은 **과거 가져오기**로 표시한다.
  최초 가져오기 뒤 라이브 이벤트나 정상 복구 열거로 새로 등록되는 항목은 일반
  자동 발견 항목이다.
- 논리 키 `(scope_id, thread_id)`로 멱등 등록해 중단 뒤 다시 실행해도 같은 항목을
  중복 생성하지 않는다.
- 쓰레드 ID, 서버·부모 채널 ID, 활동·보관 시각과 상태처럼 이 사양에 필요한
  메타데이터만 가져온다. 메시지 본문, 대화 요약, 비밀 값은 복사하지 않는다.
- 링크를 확인할 수 있는 과거 가져오기 항목은 최초 가져오기 완료 시점부터 자동
  발견 후보가 될 수 있다. 한꺼번에 다이제스트를 차지하지 않도록 아래의 단계적
  배분 규칙을 적용한다.
- 삭제, 권한 상실 또는 조회 실패로 링크를 확인할 수 없는 항목은 버리지 않고
  `접근 불가` 상태와 확인 시각을 기록한다. 접근 불가 항목은 일일 다이제스트와
  `외 N개` 계산에서는 제외한다.
- 접근 불가로 처음 판정한 날을 포함한 7개의 `Asia/Seoul` 현지 날짜에는 하루 한
  번씩 링크 가능 여부를 다시 확인한다. 계속 접근할 수 없으면 이후에는 7일마다
  확인하며 자동 삭제하지 않는다. 다시 접근할 수 있게 되면 접근 불가 상태를
  해제하고, 아직 노출되지 않은 과거 가져오기 후보로 단계적 배분에 다시 넣는다.
- 프로필별 최초 가져오기가 끝나면 설정된 Discord 채널에 아래 형식의 요약을 한
  번만 보낸다. 실제 수치는 실행 시점의 결과로 채운다.

```text
초기 가져오기: 총 X개 등록 · 링크 가능 Y개 · 접근 불가 Z개
```

## 자동 발견 시기

아직 사용자의 메시지나 명시적 확인이 관찰되지 않았고 종료되지 않은 쓰레드는
다음 두 시각 가운데 빠른 시각부터 자동 발견 후보가 된다.

1. 마지막 Hermes 활동의 `Asia/Seoul` 현지 날짜에서 3일 뒤인 날짜의 설정된 정규
   다이제스트 시각
2. 마지막 Discord 활동에 해당 쓰레드의 실제 자동 보관 기간을 더한 예상 자동
   보관 시각에서 24시간을 뺀 시각

- 실제 자동 보관 기간이나 예상 시각을 알 수 없으면 3일 규칙만 사용한다.
- 새 Hermes 활동이 첫 노출 전에 관찰되면 마지막 활동과 예상 자동 보관 시각을
  갱신해 첫 자동 발견 기준 시각을 다시 계산한다.
- 기준 시각이 되었다고 별도 즉시 알림을 만들지는 않는다. 그 시각 이후 처음
  성공하는 정규 또는 같은 날의 보충 다이제스트에서 후보가 될 수 있다.
- 정규 다이제스트가 자동 보관 전에 실행되지 못해도 후보를 버리지 않는다. Discord
  자동 보관은 삭제가 아니므로 다음 다이제스트에서 계속 표시할 수 있다.
- 사용자의 일반 메시지는 그 쓰레드의 관찰 가능한 상호작용으로 기록한다. 제어
  명령은 일반 메시지의 상태 효과를 자동 상속하지 않고 각 명령의 규칙만 적용한다.
  유효한 `!s`/`!ㄴ`과 재알림 설정은 확인 기준점을 전진시키고, `!c`/`!ㅊ`은 현재
  자동 발견 주기를 종료 상태로 닫는다. `!r -`/`!ㄱ -`와 잘못된 명령 시도는
  쓰레드 인벤토리나 확인 기준점을 바꾸지 않는다.

일반 사용자 메시지나 확인 기준점을 전진시키는 유효한 명령이 관찰될 때, 그
시점까지 수집기가 알고 있던 최신 Hermes 작업 메시지의 안정적인 Discord 메시지
ID와 시각을 **확인 기준점**으로 기록한다. 종료되지 않은 쓰레드에서 이 기준점보다
새로운 Hermes 작업 메시지가 생기면 새로운 미확인 활동 주기가 시작되고, 위와
같은 3일 규칙과 예상 자동 보관 24시간 전 규칙을 다시 적용한다.

- 새 주기 안에서 Hermes 활동이 더 생기면 최신 활동을 기준으로 자동 발견 시각을
  다시 계산한다.
- 그 뒤 사용자의 일반 메시지나 유효한 확인 명령이 관찰되면 확인 기준점을
  전진시키고 현재 자동 발견 후보에서 내린다.
- 플러그인이 보낸 명령 확인 메시지와 검토 다이제스트는 Hermes 작업 메시지로
  세지 않는다. 상태 확인 출력이 스스로 새 후보를 만드는 순환을 허용하지 않는다.
- 확인 기준점은 읽음 증명이 아니라, 재시작과 보관 복구 뒤에도 새 Hermes 활동을
  기계적으로 비교하기 위한 경계다.

## 선택적 재알림

- 이미 본 쓰레드는 사용자가 원할 때 별도의 재알림 시각을 설정할 수 있다.
- 재알림 상태는 자동 인벤토리의 발견·확인 상태와 분리한다. 하나의 쓰레드가
  인벤토리에 있으면서 동시에 활성 재알림을 가질 수 있다.
- 재알림 기록에는 다음 재알림 시각, 마지막 노출 시각, 갱신 시각을 둔다.
- 표시만으로 재알림을 자동 완료하거나 재알림 시각을 뒤로 미루지 않는다.

## 제어 명령 표면

메시지 앞뒤 공백을 제거한 뒤 첫 토큰이 알려진 명령 글자이면 제어 명령 시도로
인식하고, 전체 메시지가 아래 문법과 맞을 때 상태를 변경한다. 영문은 대소문자를
구분하지 않는다. 명령 글자와 일수 단위는 같은 두벌식 키 입력을 각각 정규화하므로
영문과 한글을 섞은 형태도 허용한다.

| 명령 | 두벌식 키 별칭 | 동작 |
| --- | --- | --- |
| `!s` (Seen) | `!ㄴ` | 현재 쓰레드를 확인한 것으로 기록하고 자동 발견 후보에서 내린다. 종료 상태라면 다시 열며 활성 재알림은 바꾸지 않는다. |
| `!r Nd` (Remind) | `!ㄱ Nㅇ` | N일 뒤 현지 날짜의 정규 다이제스트로 재알림을 설정하거나 기존 예약을 변경한다. 종료 상태라면 다시 연다. |
| `!r -` | `!ㄱ -` | 활성 재알림만 취소한다. 인벤토리·확인·종료 상태는 바꾸지 않는다. |
| `!c` (Coda/Close) | `!ㅊ` | 쓰레드를 종료하고 자동 발견 후보에서 내리며 활성 재알림도 취소한다. 이후 수동으로 다시 열기 전까지 새 Hermes 활동만으로는 재개하지 않는다. |

- 정규화 쌍은 `c ↔ ㅊ`, `s ↔ ㄴ`, `r ↔ ㄱ`, `d ↔ ㅇ`이다.
- `!r Nd`의 N은 1 이상 3650 이하의 십진 정수다. `!r 30d`, `!ㄱ 30d`,
  `!r 30ㅇ`, `!ㄱ 30ㅇ`은 모두 같은 의미다.
- N일은 정확히 N×24시간 뒤가 아니라 `Asia/Seoul` 기준 N일 뒤 현지 날짜를 뜻한다.
  해당 날짜의 설정된 정규 다이제스트 시각에 후보가 되며 기본 시각은 오전 9시다.
- 같은 쓰레드에서 재알림을 다시 설정하면 기존 활성 예약을 새 값으로 덮어쓴다.
- 재알림 설정 명령 자체도 관찰 가능한 사용자 상호작용이므로 현재 쓰레드를 확인한
  것으로 기록한다.
- 폐기된 초기 ADR의 `!t`, `!done`은 역사적 예시일 뿐 현재 사양이 아니다.
- 첫 버전의 명령 표면은 이 절의 `!s`, `!r`, `!c` 세 글자와 한글 키 별칭으로
  닫는다. 상태 조회, 별도 snooze, 절대 날짜·시각 예약 명령은 추가하지 않는다.
  상대적인 미루기는 기존 `!r Nd`가 담당한다.

`!c`, `!ㅊ`, `!s`, `!ㄴ`, `!r`, `!ㄱ` 중 하나로 시작한 전체 메시지는 인자가
잘못되어도 인식된 제어 명령 시도다. 권한 있는 사용자의 이런 시도는 플러그인에서
끝내며 LLM으로 보내지 않는다. 그 밖의 `!` 메시지는 이 플러그인이 소유하지 않는다.

## 명령 확인 응답

별도 도움말 명령은 두지 않는다. 권한 있는 사용자의 인식된 제어 명령 시도에는
성공·실패와 관계없이 다음 두 부분을 한 Discord 확인 메시지로 보낸다.

1. `✅` 또는 `❌`로 시작하는 구체적인 처리 결과 한 줄
2. 현재 지원하는 전체 명령 목록 한 줄

2026-08-28에 실행한 성공 예시는 다음과 같다.

```text
✅ !ㄱ 30ㅇ → 30일 뒤(2026-09-27 오전 9시) 다이제스트로 예약됨
명령: !s/!ㄴ 확인 · !r 30d/!ㄱ 30ㅇ 재알림 · !r -/!ㄱ - 취소 · !c/!ㅊ 종료
```

잘못된 인자의 예시는 다음과 같다.

```text
❌ `30ㄷ`은 인식할 수 없음
명령: !s/!ㄴ 확인 · !r 30d/!ㄱ 30ㅇ 재알림 · !r -/!ㄱ - 취소 · !c/!ㅊ 종료
```

결과와 목록은 코드에 정의한 단일 고정 템플릿에서 만들며 LLM을 호출하지 않는다.
재알림 성공 결과에는 상대 일수와 실제 적용될 현지 날짜·다이제스트 시각을 함께
표시한다.

## 명령 reaction

권한 있는 사용자의 인식된 제어 명령 시도에는 다음 고정 reaction 의미를 사용한다.

- 처리를 시작하면 `⏳`를 붙인다.
- 유효한 명령의 상태 변경 트랜잭션이 커밋되거나, 이미 원하는 상태여서 추가 변경이
  필요 없는 유효한 명령 처리가 끝나면 `⏳`를 제거하고 `✅`를 붙인다.
- 문법·인자가 잘못되었거나 DB 오류로 상태를 커밋하지 못하면 `⏳`를 제거하고 `❌`를
  붙인다. 이때 장부 상태는 바뀌지 않은 것으로 해석한다.
- 상태 커밋 뒤 확인 메시지 전송만 실패한 경우에는 `✅`를 유지한다. `✅`는 확인
  메시지 전달 여부가 아니라 명령의 장부 적용 성공을 뜻한다.
- reaction 쓰기 자체가 실패해도 커밋한 상태를 되돌리거나 명령을 다시 적용하지
  않는다. 내구성 있는 처리 결과는 전달 장부의 확인 메시지가 보완한다.

## 전달 장부와 재시도

플러그인이 만드는 제어 명령 확인, 최초 가져오기 요약, 검토 다이제스트는 Discord에
보내기 전에 프로필 로컬 **전달 장부**에 내구성 있는 전달 의무로 기록한다.

- 전달 의무에는 종류, 안정적인 논리 키, 대상 채널 또는 쓰레드, 시도 횟수, 다음
  시도 시각, 마지막 오류, 전달·대체·전달 중단 상태와 갱신 시각을 둔다.
- 논리 키는 제어 명령 확인의 경우 원본 Discord 메시지 ID, 최초 가져오기 요약의
  경우 프로필의 최초 가져오기 ID, 검토 다이제스트의 경우 `Asia/Seoul` 현지 날짜를
  포함한다. 같은 논리 키를 다시 처리해도 전달 의무를 중복 생성하지 않는다.
- 원본 제어 명령 메시지 전체는 저장하지 않는다. 검증된 결과 코드와 필요한 최소
  인자만 저장하고 고정 템플릿으로 같은 확인 문구를 다시 만든다. 최초 가져오기
  요약은 완료 시 확정한 개수만 저장하며, 다이제스트 재시도는 현재 장부에서 내용을
  다시 만든다.
- 전송이 실패하거나 성공 여부가 불확실하면 첫 실패 1분 뒤, 두 번째 실패 5분 뒤,
  세 번째 실패 30분 뒤, 이후에는 3시간 간격으로 다시 시도한다. 프로세스가 재시작해도
  시도 횟수와 다음 시각을 이어 간다.
- 제어 명령 확인과 최초 가져오기 요약은 성공할 때까지 같은 전달 의무만 재시도한다.
  명령 상태 변경이나 최초 가져오기를 다시 실행하지 않는다.
- 일일 다이제스트만 날짜 경계를 예외로 둔다. 해당 현지 날짜 안에서 위 간격으로
  재시도하되, 다음 현지 날짜가 되면 미전달된 전날 의무를 `대체됨`으로 기록하고
  보내지 않는다. 새 날짜의 현재 상태로 다이제스트 하나를 만든다.
- Discord가 메시지를 받은 직후 성공 기록 전에 프로세스가 중단되면 재시도 메시지가
  드물게 중복될 수 있다. 누락을 피하기 위한 최소 한 번 전달 정책의 한계로
  허용한다.

첫 번째 전송에는 기술적인 시도 번호를 표시하지 않는다. 두 번째 이후 전송에는
다음 고정 형식을 사용한다.

- 제어 명령 확인은 첫 결과 줄 앞에 `↻ 지연 확인 · `을 붙인다. `✅` 또는 `❌`와
  전체 명령 목록은 원래 처리 결과를 그대로 보여 준다.
- 최초 가져오기 요약은 `↻ 초기 가져오기 · 재시도 N` 머리말을 붙인다.
- 모든 다이제스트 제목에는 현지 날짜를 넣는다. 첫 시도는
  `Hermes 검토 · 2026-08-28`, 두 번째 이후는
  `Hermes 검토 · 2026-08-28 · 재시도 N` 형식이다.
- 여기서 N은 전달 장부의 실제 전송 시도 번호다. 같은 날짜의 제목이 둘 이상 보이면
  같은 날 전달이 중복되었을 수 있음을 알 수 있다. 재시도 시 현재 장부로 내용을
  다시 만들기 때문에 두 메시지의 항목 구성은 달라질 수 있다.

Discord가 대상 삭제나 권한 상실처럼 재시도로 해결되지 않는 오류를 명확히 반환하면
다음과 같이 처리한다.

- 원본 쓰레드로 제어 명령 확인을 보낼 수 없으면 해당 전달 의무를 `전달 중단`으로
  기록하고, 설정된 다이제스트 채널에 장부 적용 성공 여부와 쓰레드 참조만 담은
  고정 경고를 보낸다. 원본 명령 본문은 포함하지 않는다.
- 설정된 다이제스트 채널 자체로 보낼 수 없으면 별도 Discord 채널을 추측해 사용하지
  않는다. 원인과 시작 시각을 Hermes 로컬 운영 로그에 남기고 기존 주기로 접근
  복구를 확인한다.
- 다이제스트 채널이 다시 사용 가능해지면 중단 시작·복구 시각을 담은 고정 경고를
  그 채널에 한 번 보내고 정상 전달을 재개한다.
- 이 경고와 재시도 표시는 모두 코드의 고정 템플릿으로 만들며 LLM을 호출하지 않는다.

## 처리 계약

인식된 제어 명령은 다음 순서로 처리한다.

1. Discord 어댑터가 메시지를 `MessageEvent`로 정규화하고, 읽기 전용 제어 분류로
   batch·바쁜 세션의 일반 텍스트 병합 대상에서 분리한다.
2. 코어가 일반 Hermes와 동일한 권한 결정을 한 번 계산해
   `pre_gateway_dispatch` 훅에 전달한다.
3. 훅이 정확한 제어 명령인지 판별하고 권한 결과가 참일 때만 처리한다.
4. 문법과 인자를 검증한다. 유효하면 쓰레드 인벤토리 또는 재알림 장부의 변경과
   제어 명령 확인 전달 의무를 한 트랜잭션에서 기록한다. 잘못된 인자라면 상태는
   바꾸지 않고 실패 확인 전달 의무만 기록한다.
5. 플러그인이 전달 장부를 통해 고정 템플릿의 결과와 전체 명령 목록을 Discord에
   보낸다.
6. 훅이 `skip`을 반환해 세션·대화 기록·에이전트·LLM 경로로 보내지 않는다.
7. 위 `명령 reaction` 절에 따라 처리 중·성공·실패 reaction을 갱신한다.

같은 원본 Discord 메시지 ID가 이벤트 복구나 재시작으로 다시 들어오면 기존 처리
결과와 전달 의무를 사용한다. 상태 변경을 다시 적용하거나 N일 뒤 날짜를 다시
계산하지 않는다. DB 변경이 커밋된 뒤 확인 메시지 전송이 실패해도 상태를
되돌리지 않고 확인 메시지만 재시도한다.

일반 사용자 메시지는 기존 Hermes 경로로 계속 처리하면서 해당 쓰레드에 관찰
가능한 사용자 상호작용이 있었다는 사실을 인벤토리에 반영한다. 종료된 쓰레드의
일반 사용자 메시지, 유효한 `!s`/`!ㄴ`, 유효한 `!r Nd`/`!ㄱ Nㅇ`은 종료 상태를
해제한다. `!r -`/`!ㄱ -`, 잘못된 제어 명령 시도, Hermes의 수동적 새 활동은 종료
상태를 해제하지 않는다. 확인·종료 상태를 같은 행에 둘지 별도 행에 둘지는 외부
동작을 바꾸지 않는 가역적 구현 세부사항이다.

## 명령 기록과 히스토리 격리

- 처리한 제어 명령 원문은 Discord에서 자동 삭제하거나 수정하지 않는다. 사용자는
  원본 명령, reaction과 고정 확인 메시지를 그대로 보고 처리 이력을 확인할 수 있다.
- 권한 있는 사용자의 인식된 제어 명령 시도는 성공·문법 실패와 관계없이 원본
  Discord 메시지 ID를 **히스토리 제외 장부**에 기록한다. 유효한 명령이면 상태 변경,
  확인 전달 의무와 같은 SQLite 트랜잭션에서 기록하고, 잘못된 명령이면 실패 확인
  전달 의무와 같은 트랜잭션에서 기록한다.
- 플러그인이 보낸 제어 명령 확인 메시지는 Discord가 반환한 모든 메시지 ID를 같은
  장부에 추가하고 `non_conversational` 전송 메타데이터를 사용한다. 한 확인이 여러
  Discord 메시지로 나뉘거나 최소 한 번 전달 재시도로 중복되어도 반환받은 ID를
  모두 기록한다.
- 원본 명령 ID와 확인 메시지 ID는 현재 Hermes 프로필이 명시적으로 초기화될 때까지
  만료나 개수 제한 없이 보존한다. 장부에는 ID, 메시지 종류와 필요한 최소 연결
  식별자만 두며 명령 원문, 확인 문구 본문, 비밀 값은 저장하지 않는다.
- 실시간 진입, 누락 메시지 복구, 최근 채널 문맥 수집과 답장 대상 주변 문맥 수집을
  포함해 Discord 메시지로 Hermes 입력을 만드는 모든 경로는 이 장부의 ID를
  제외한다. 따라서 즉시 가로챈 명령이 나중에 세션 기록이나 LLM 입력으로 우회해
  들어가서는 안 된다.
- DB 실패나 원본 ID 기록 직전의 프로세스 중단으로 제외 장부 행이 없을 때도 같은
  결론을 유지한다. 히스토리 수집은 권한 있는 사용자의 쓰레드 메시지에 동일한
  결정적 제어 명령 시도 판별기를 보조 규칙으로 적용해 일치한 원문을 제외하되,
  상태 변경이나 확인 메시지 재생성은 하지 않는다.
- Discord가 확인 메시지를 받은 직후 ID를 장부에 기록하기 전에 프로세스가 중단되는
  경계도 고려한다. 반환 ID 기록과 함께, 현재 봇이 작성한 정확한 고정 확인 템플릿을
  히스토리 수집에서 비대화형 메시지로 판별하는 보조 규칙을 둔다. 이 보조 규칙은
  사용자 메시지나 일반 Hermes 답변에 적용하지 않는다.
- 제어 명령과 고정 확인 메시지는 새 Hermes 작업 활동으로 세지 않는다. 명령이
  확인·종료·재알림 상태에 주는 영향은 각 명령의 명시된 동작만 따른다.

## 안전 규칙

- 제어 명령을 보낸 사용자의 권한 검사에 실패하면 장부를 변경하지 않는다. 이는
  `설정 오류 상태`의 Hermes 봇 채널 조회·전송 권한 실패와 구분한다.
- Discord 쓰레드 안에서 온 명령만 처리한다.
- 인벤토리, 재알림 장부, 전달 장부, 히스토리 제외 장부는 현재 Hermes 프로필에
  로컬로 둔다.
- 메시지 본문, 대화 요약, 비밀 값은 인벤토리나 장부에 저장하지 않는다.
- 자동 동작은 Hermes 봇 계정으로만 수행한다.

## 설정과 활성화

기존 `discord-related-threads` 플러그인 전체의 활성 상태와 새 쓰레드 관심 기능의
활성 상태를 분리한다. 플러그인은 기존 관계 도구와 관련 쓰레드 표시를 위해 계속
`plugins.enabled`에 둘 수 있고, 새 기능만 아래 프로필 로컬 `config.yaml` 블록으로
켠다.

```yaml
plugins:
  enabled:
    - discord-related-threads
  entries:
    discord-related-threads:
      thread_attention:
        enabled: true
        digest_channel_id: "DISCORD_CHANNEL_ID"
        digest_time: "09:00"
        timezone: "Asia/Seoul"
```

- 사람이 검토하는 전용 Discord 채널의 권장 이름은 `#hermes-review`다. 이 이름은
  운영자가 알아보기 위한 관례이며 런타임 식별자는 아니다. 플러그인은 채널 이름을
  검색하거나 같은 이름의 채널을 자동 생성하지 않고, 설정한 `digest_channel_id`만
  사용한다.
- `plugins.entries.discord-related-threads.thread_attention.enabled`가 없거나 `false`면
  새 기능은 기본 비활성이다. 코드가 설치되어 있어도 자동 인벤토리 수집, 과거
  가져오기, 검토 스케줄과 새 Discord 전송을 시작하지 않는다.
- 기능을 사용하도록 배포할 때 `enabled: true`를 한 번 저장한다. 이 값은
  `config.yaml`에 남으므로 이후 게이트웨이를 재시작할 때 다시 입력할 필요가 없다.
- `enabled: true`일 때 `digest_channel_id`는 필수이며 Discord snowflake를 문자열로
  저장한다. `digest_time`은 24시간제 `HH:MM`이고 생략 시 `09:00`, `timezone`은
  IANA 시간대 이름이고 생략 시 `Asia/Seoul`이다.
- 첫 버전은 게이트웨이 시작 시 설정을 읽는다. 파일을 수정한 뒤에는 게이트웨이를
  정상 재시작해야 새 활성 상태와 일정이 적용된다.
- 이 기능이 비활성이어도 기존 쓰레드 관계 DB, 관계 도구와 관련 쓰레드 footer는
  그대로 유지한다. 비활성화는 기존 장부나 인벤토리 행을 삭제하는 초기화가 아니다.

### 설정 오류 상태

`enabled: true`지만 정적 설정이 잘못되었거나, 지정한 다이제스트 채널을 찾을 수
없거나, Hermes 봇이 그 채널을 조회·전송할 수 없으면 새 기능은 **설정 오류 상태**로
시작한다.

- 자동 인벤토리 수집, 과거 가져오기, 검토 스케줄과 기존 전달 의무의 전송을
  시작하지 않는다. 인벤토리·확인·종료·재알림 상태도 바꾸지 않는다.
- 기존 쓰레드 관계 도구와 footer, 일반 Hermes 메시지 경로는 계속 동작한다.
- 권한 있는 사용자의 인식된 제어 명령은 오류 중에도 `pre_gateway_dispatch`에서
  가로채 에이전트·LLM으로 보내지 않는다. 원본 메시지 ID는 가능한 경우 히스토리
  제외 장부에 남기되, 명령이 요청한 인벤토리·종료·재알림 변경은 적용하지 않는다.
- 원본 쓰레드에 보낼 수 있으면 `❌` reaction과 아래 고정 응답을 사용한다. 전체
  명령 목록은 정상·문법 오류 응답과 같은 단일 템플릿에서 붙이며 LLM을 호출하지
  않는다.

```text
❌ 다이제스트 채널 설정 오류: 채널 ID 또는 봇 권한을 확인해 주세요
명령: !s/!ㄴ 확인 · !r 30d/!ㄱ 30ㅇ 재알림 · !r -/!ㄱ - 취소 · !c/!ㅊ 종료
```

- 원본 쓰레드에도 응답하거나 reaction을 쓸 수 없으면 다른 Discord 채널을 추측하지
  않고 로컬 운영 로그에 남긴다. 어떤 경우에도 해당 명령을 일반 프롬프트로 되돌리지
  않는다.
- 설정 오류 원인은 게이트웨이 시작마다 한 번 로컬 운영 로그에 남긴다. 같은 오류를
  이벤트마다 반복 기록해 로그를 범람시키지 않는다.
- `Add Reactions`처럼 부가적인 source-thread reaction 권한만 없는 것은 기능 전체의
  활성화 차단 사유가 아니다. reaction은 최선 노력으로 처리하고 전달 장부와 고정
  확인 메시지를 상태의 근거로 사용한다.
- 채널이나 권한을 고친 뒤 게이트웨이를 정상 재시작하면 설정을 다시 검증한다.
  통과하면 기존 DB를 지우지 않고 멱등한 최초 활성화 흐름을 이어 간다.

### 최초 활성화와 재개

설정이 정상일 때 첫 활성화는 아래 순서로 진행한다.

1. `config.yaml`의 구조·필수 값·시각·시간대를 정적으로 검증한다.
2. 추가 전용 DB 마이그레이션과 `quick_check`를 끝내고 필요한 테이블·인덱스를
   확인한다.
3. Discord에 연결한 뒤 지정 다이제스트 채널의 존재와 Hermes 봇의 조회·전송
   권한을 검증한다.
4. 한 SQLite 트랜잭션에서 프로필별 활성화 ID, 시작 시각과 당시 영속 참여 쓰레드
   ID 집합을 **과거 가져오기 스냅샷**으로 고정한다. 이미 진행 중인 활성화가 있으면
   새 ID나 스냅샷을 만들지 않고 기존 것을 사용한다.
5. 새 라이브 쓰레드 수집과 전달 장부 worker를 먼저 시작한다. 스냅샷에 든 쓰레드는
   처리 중 라이브 이벤트가 다시 와도 과거 가져오기 분류를 유지하고, 스냅샷에 없는
   새 쓰레드는 일반 자동 발견 항목으로 멱등 등록한다.
6. 고정한 스냅샷을 제한된 batch로 처리한다. 각 항목의 완료 여부를 영속 저장해
   프로세스가 중단되어도 완료하지 못한 항목부터 이어 간다.
7. 모든 스냅샷 항목의 처리가 끝나면 한 트랜잭션에서 활성화를 `준비 완료`로 바꾸고,
   확정한 총 등록·링크 가능·접근 불가 수치로 최초 요약 전달 의무를 정확히 한 번
   만든다.
8. 위 트랜잭션이 커밋된 뒤 검토 다이제스트 스케줄을 연다. 최초 요약의 일시적인
   전송 실패와 재시도는 다이제스트 자체를 무기한 막지 않는다.
9. `준비 완료`가 된 현지 날짜의 설정 시각이 이미 지났고 그날 성공한 다이제스트가
   없다면, 현재 장부를 사용한 같은 날의 보충 다이제스트를 한 번 실행한다. 과거
   날짜의 다이제스트를 날짜별로 재생하지 않는다.

초기화 중 게이트웨이가 재시작되면 같은 활성화 ID와 스냅샷을 다시 읽는다. 실시간
수집을 다시 연 뒤 미완료 batch만 처리하고, 이미 완료한 항목·최초 요약·같은 날짜의
성공한 다이제스트를 중복 생성하지 않는다. 최초 활성화가 완료된 뒤 채널·시각을
바꾸거나 기능을 껐다 다시 켜는 것은 새 과거 가져오기를 만들지 않는다. 다시 켤 때
현재 영속 참여 ID와 인벤토리를 한 번 대조해 꺼져 있던 동안 생긴 누락 ID만 live
항목으로 등록한 뒤 기존 장부에서 정상 운영을 재개한다.

## 수명주기

- Discord 자동 보관은 인벤토리나 재알림 항목을 삭제·완료시키지 않는다.
- 일반 프롬프트는 Discord 활동 시각을 갱신하고 관찰 가능한 사용자 상호작용으로
  기록되며, 종료된 쓰레드를 다시 연다. 다만 업무 완료나 실제 열람 전체를
  증명하지 않는다.
- 종료 상태는 수동적 Hermes 활동과 Discord 보관·복구로 해제되지 않는다.
- 원래 쓰레드를 살려 두기 위한 keepalive 메시지는 반복해서 보내지 않는다.
- 같은 쓰레드의 에이전트 턴이 진행 중이어도 인식된 제어 명령은 일반 prompt queue와
  합치지 않고 별도로 `pre_gateway_dispatch`까지 전달한다. 진행 중인 에이전트 턴은
  취소하지 않는다.
- 가로챈 제어 명령 원문은 Discord에는 남지만, 히스토리 제외 장부 때문에 향후
  Discord 히스토리 역수집·문맥 수집에서도 Hermes 세션이나 LLM 입력에 들어가지
  않는다.

## 검토 다이제스트

- 다이제스트는 `Asia/Seoul` 현지 날짜를 기준으로 하루 한 번 실행한다. 기본
  실행 시각은 오전 9시이며 설정으로 바꿀 수 있다.
- 제목은 `Hermes 검토 · YYYY-MM-DD` 형식으로 해당 현지 날짜를 항상 표시한다.
- 후보가 있으면 제목 다음 줄에 `표시 X개`를 쓰고, 표시하지 못한 후보가 있을 때만
  ` · 외 N개`를 덧붙인다.

각 항목은 기본적으로 다음 한 줄 형식을 사용한다.

```text
N. [쓰레드 이름](Discord 링크) — 이유 라벨 · 시각 정보
```

- 이유 라벨은 `미확인`, `새 활동`, `과거`, `보관 임박`, `재알림` 다섯 개만 쓴다.
- 기본 자동 발견 이유는 하나만 고른다. 사용자의 첫 상호작용 전 일반 항목은
  `미확인`, 확인 기준점 뒤 새 Hermes 활동은 `새 활동`, 아직 사용자 상호작용이
  없었던 최초 가져오기 항목은 `과거`다.
- 예상 자동 보관 24시간 전 규칙이 3일 규칙보다 먼저 후보를 만들었으면
  `보관 임박`을 추가한다. 활성 명시적 재알림이 병합된 항목에는 `재알림`을
  추가한다.
- 여러 이유는 `새 활동+재알림`처럼 `미확인`·`새 활동`·`과거`, `보관 임박`,
  `재알림` 순서로 `+`를 사용해 합친다.
- `미확인`, `새 활동`, `과거`에는 `Hermes 활동 N시간 전` 또는
  `Hermes 활동 N일 전`을 붙인다. 하루 이상은 `Asia/Seoul` 현지 날짜 차이를,
  하루 미만은 경과한 전체 시간을 사용한다.
- `보관 임박`에는 예상 시각이 남아 있으면 `보관까지 약 N시간`, 이미 보관되었으면
  `보관됨`을 붙인다.
- `재알림`에는 다이제스트와 같은 현지 날짜면 `예약 오늘 HH:MM`, 다른 날짜면
  `예약 MM-DD HH:MM`을 붙인다.
- 겹친 항목은 한 링크만 쓰고 각 이유에 필요한 시각 정보를 ` · `로 연결한다.
- 쓰레드 이름이 길어 항목이 두 줄을 넘으려 하면 표시 이름만 말줄임하고 Discord
  링크 대상은 바꾸지 않는다. 정확한 글자 수는 Discord 모바일 렌더링 테스트로
  정한다.
- 메시지 본문, 발췌, 대화 요약은 표시하지 않으며 항목 생성을 위해 LLM을 호출하지
  않는다.

예시는 다음과 같다.

```text
Hermes 검토 · 2026-08-28
표시 3개 · 외 12개

1. [배포 오류 조사](https://discord.example/thread/1) — 미확인 · Hermes 활동 3일 전
2. [API 설계 검토](https://discord.example/thread/2) — 재알림 · 예약 오늘 09:00
3. [리서치 정리](https://discord.example/thread/3) — 새 활동+재알림 · Hermes 활동 4일 전 · 예약 오늘 09:00
```

- 예약 시각에 Hermes가 실행 중이지 않았다면, 같은 현지 날짜 안에 다시 시작한
  시점이 예약 시각 이후이고 그날 성공한 다이제스트가 없을 때 한 번만 보충
  실행한다.
- 이전 날짜에 놓친 다이제스트를 날짜별로 재생하지 않는다. 보충 실행도 실행
  시점의 현재 인벤토리와 재알림 장부를 조회해 다이제스트 하나만 만든다.
- 검토 결과는 설정으로 지정한 Discord 채널 하나로 라우팅한다.
- 실행 시점에 다시 볼 쓰레드가 0개여도 날짜 제목 다음 줄에 `오늘 다시 볼 쓰레드는
  0개입니다.`라고 쓴 빈 상태 다이제스트를 지정 채널에 보낸다. Discord가 이
  메시지의 성공을 확인하면 해당 날짜의 다이제스트를 성공한 실행으로 기록한다.
- 다이제스트 전달 보장은 최소 한 번 전달(at-least-once)이다. Discord가 성공을
  확인해 주기 전에는 해당 날짜를 성공한 실행으로 기록하지 않고, 포함 항목의
  마지막 노출 시각도 갱신하지 않는다.
- 전송 실패 또는 성공 여부가 불확실한 실행은 전달 장부의 재시도 가능 상태로
  남긴다. 재시도 간격과 날짜가 바뀔 때의 대체 규칙은 `전달 장부와 재시도` 절을
  따른다.
- 재시도할 때는 최초 전송 시도의 항목 집합을 보존하지 않고 현재 인벤토리와
  재알림 장부를 다시 조회해 다이제스트를 새로 만든다. 그 사이 확인·종료되거나
  미래로 다시 예약된 항목은 빠지고, 새로 다시 볼 때가 된 항목은 들어올 수 있다.
- 한 번의 다이제스트에는 다시 볼 쓰레드를 최대 10개까지 표시한다.
- 표시 대상이 10개를 넘으면 요약 줄의 `외 N개`에 이번 다이제스트에 표시하지 못한
  중복 제거 후의 고유 후보 수를 쓴다.
- 같은 `(scope_id, thread_id)`에 자동 발견과 명시적 재알림이 함께 걸리면 한 항목으로
  합치고 두 이유를 함께 표시한다. 이 항목의 다시 볼 기준 시각은 두 시각 중 빠른
  값이며, 10개 배분에서는 명시적 재알림 후보로 센다.
- 중복 제거 뒤 자동 발견 후보와 명시적 재알림 후보에서 기본 5개씩 고른다. 한쪽이
  5개보다 적으면 남는 자리를 다른 쪽 후보로 채워 총 10개까지 표시한다.
- 자동 발견의 기본 5칸에서는 최초 가져오기 뒤 정상 운영 중 등록된 후보가 3개
  이상이면 그중 3칸을 먼저 보장하고, 과거 가져오기 후보는 기본적으로 최대 2칸을
  고른다. 둘 중 한쪽이 부족하면 다른 쪽이 빈 기본 자리를 채운다. 기본 배분이나
  재알림 쪽에서 자리가 더 남으면 과거 가져오기 후보도 2개를 넘어 총 10개 한도
  안에서 남는 자리를 채울 수 있다.
- 각 후보군 안에서는 아직 한 번도 노출되지 않은 항목을 먼저 고른다. 그다음은
  마지막 노출 시각이 가장 오래된 항목부터 고른다.
- 아직 노출되지 않은 과거 가져오기 후보끼리는 마지막 Hermes 활동이 최근인
  항목부터 고른다. 이 우선순위와 미노출 우선 규칙 때문에 최근 과거분부터 시작하되
  결국 링크 가능한 과거분 전체가 최소 한 번씩 순환한다.
- 그 밖의 동률이면 각 후보가 다시 볼 때가 된 기준 시각이 오래된 항목부터 고르고,
  마지막에는 안정적인 쓰레드 식별자 순서를 사용해 실행마다 순서가 흔들리지 않게
  한다.
- 성공적으로 표시한 항목에는 마지막 노출 시각을 기록한다. 표시만으로 후보를 자동
  확인·완료하거나 재알림 시각을 뒤로 미루지 않는다.
- 사용자가 아무 상호작용도 하지 않은 표시 항목은 성공한 노출 뒤 3일 동안 정규
  재노출 대상에서 제외하고, 세 번째 `Asia/Seoul` 현지 날짜의 정규 다이제스트부터
  다시 후보가 될 수 있다. 마지막 노출 뒤 사용자가 새로 설정하거나 변경한 명시적
  재알림 시각이 그보다 빠르면 해당 예약 시각이 이 재노출 제한보다 우선한다.
- 원래 쓰레드에는 자동 메시지를 보내거나 keepalive를 수행하지 않는다.

## 첫 버전 범위 밖

상태 조회, 별도 snooze, 절대 날짜·시각 예약은 첫 버전에 넣지 않는다. 필요성이
확인되면 기존 한 글자 명령 표면과 충돌하지 않는 후속 사양으로 다시 검토한다.
