# Product definition

## 목표

Chris가 아직 들여다보지 못한 Hermes Discord 작업 쓰레드도 일반 쓰레드 목록에서
사라지기 전이나 사라진 뒤에 최소 한 번 인지 영역으로 들어오게 한다. 이미 본
쓰레드 가운데 나중에 다시 확인할 열린 고리는 사용자가 직접 시점을 정해 짧고
실행 가능한 알림으로 되돌아오게 한다.

## 확인된 핵심 위험

- 주된 위험은 사용자가 쓰레드를 한 번도 열어보거나 상호작용하지 못한 채 Discord
  자동 보관으로 일반 목록에서 사라지는 것이다.
- 사용자가 이미 찾은 쓰레드에 아무 메시지나 보내는 방법은 그 쓰레드의 활동
  시각만 갱신한다. 아직 찾지 못한 쓰레드에는 적용할 수 없으므로 핵심 위험의
  완전한 대응책이 아니다.
- Discord가 봇에게 사용자의 단순 열람 여부를 알려주지 않는 범위에서는, 시스템이
  관찰할 수 있는 사용자 메시지·명시적 확인을 열람의 대용 신호로 써야 한다.

## 합의된 제품 원칙

- Hermes가 만들거나 참여한 쓰레드는 사용자의 방문이나 명령 없이 자동
  인벤토리에 등록한다.
- 자동 인벤토리는 아직 발견하지 못한 쓰레드를 포착하고, 선택적 재알림은 이미
  본 쓰레드를 나중에 다시 보게 하는 별도 층으로 둔다.
- 사용자의 메시지나 명시적 확인은 "확인함"의 관찰 가능한 대용 신호다. 단순히
  열어 읽었는지는 정확히 안다고 주장하지 않는다.
- 제어 명령은 LLM을 호출하지 않고 내구성 있게 상태를 기록한다.
- 제어 명령은 `!`와 영문 한 글자를 기본으로 하고, 같은 두벌식 키의 한글 입력도
  같은 명령으로 인식한다.
- 모든 인식된 제어 명령 시도에는 에이전트 답변 대신 플러그인의 고정 결과 한 줄과
  전체 명령 목록 한 줄을 보여 준다. 이 확인에는 LLM을 사용하지 않는다.
- 첫 버전의 제어 명령은 확인·재알림·종료로 닫고, 별도 상태 조회·snooze·절대 날짜
  예약은 추가하지 않는다. 상대적인 미루기는 재알림 명령으로 처리한다.
- 처리한 제어 명령은 Discord에서 지우지 않아 사람이 처리 이력을 볼 수 있게 하되,
  원본과 플러그인 확인 메시지의 ID를 보존해 이후 Hermes 히스토리와 LLM 입력에서는
  계속 제외한다.
- 성공한 제어 명령에는 기존 Discord 반응(reaction)도 사용할 수 있다.
- 일일 알림은 자동 발견 후보와 명시적 재알림 후보를 합쳐 제한된 개수로 보여 준다.
- 확인한 쓰레드도 확인 기준점 뒤에 새 Hermes 활동이 생기면 다시 자동 발견 대상이
  된다. 종료한 쓰레드는 사용자가 명시적으로 다시 열기 전까지 닫힌 상태를 유지한다.
- 같은 쓰레드의 자동 발견과 재알림은 한 항목으로 합치고, 최대 10칸은 두 후보군에
  기본 5칸씩 배분하되 남는 칸을 서로 넘긴다.
- 표시했지만 사용자가 조치하지 않은 항목은 매일 반복하지 않고 3일 간격으로 다시
  보여 준다. 그보다 이른 새 명시적 재알림은 예약 시각을 따른다.
- 기능을 처음 켤 때 기존 Hermes 참여 쓰레드는 기간 제한 없이 메타데이터만 모두
  가져온다. 과거분은 단계적으로 노출해 새 쓰레드의 자리를 보장한다.
- 삭제·권한 상실 등으로 링크할 수 없는 과거 항목은 버리지 않고 별도 상태로
  기록하되 일일 검토 목록에는 넣지 않는다.
- 플러그인의 확인·요약·다이제스트는 보내기 전에 전달 장부에 기록해 재시작 뒤에도
  재시도한다. 확인 메시지 실패 때문에 이미 커밋한 명령 상태를 되돌리지 않는다.
- 전날 실패한 다이제스트를 뒤늦게 쌓아 보내지 않고, 다음 날 최신 상태의 목록으로
  대체한다.
- 명령 reaction은 `⏳` 처리 중, `✅` 장부 적용 성공, `❌` 미적용을 뜻한다. 재시도된
  확인과 다이제스트에만 지연·시도 번호를 표시해 정상 메시지는 간결하게 유지한다.
- 원본 쓰레드 전달 중단은 지정 다이제스트 채널에, 다이제스트 채널 자체의 중단은
  로컬 운영 로그와 복구 후 1회 경고로 드러낸다.
- 다이제스트 항목은 쓰레드 링크, 짧은 이유 라벨, 관련 시각만 한두 줄로 보여 준다.
  메시지 본문이나 LLM 요약 없이도 왜 지금 목록에 올랐는지 판단할 수 있어야 한다.
- Discord 자동 보관 여부와 인벤토리·재알림 상태는 서로 독립적이다.

## 채택한 해결 방식

모든 Hermes 참여 쓰레드를 자동 인벤토리에 넣고, 이미 본 쓰레드의 의도적인
재확인은 선택적 재알림으로 관리하는 2층 구조를 쓴다. 수동 명령은 자동 발견의
전제조건이 아니라 확인·종료·재알림을 표현하는 보조 수단이다.

## 제약

- 기존 Hermes Discord 봇, `discord-related-threads` 플러그인, 공식 Hermes 플러그인
  API와 SQLite 기반을 재사용한다.
- 릴리스는 수정하지 않은 공식 Hermes의 지원 버전 위에 플러그인 하나만 설치한다.
  사용자 유지 Hermes 포크, 설치 시 코어 패치, 라이브 코어 파일 교체를 요구하지
  않는다.
- 코어가 계산한 일반 게이트웨이 인증 결과를 재사용하고, 플러그인은 승인된
  이벤트에만 상태 변경을 적용한다. 부족한 호스트 기능은 기능 로직이 아닌 최소
  범용 계약으로 Hermes upstream에 제안한다.
- 필요한 공식 호스트 계약이 없는 Hermes 버전에서는 기능을 조용히 축소하거나
  비공개 adapter monkeypatch로 우회하지 않고 호환성 오류로 활성화를 막는다.
- 두 번째 봇·별도 데몬·모델 노출 도구·self-bot을 만들지 않는다.
- 기존 플러그인이 관리하는 쓰레드 관계 기능을 보존한다.

## 하지 않는 일

- 모든 쓰레드에 주기적으로 메시지를 보내 자동 보관을 막지 않는다.
- 메시지 내용을 모델로 읽어 모든 열린 일을 자동 추론하지 않는다.
- 과거 쓰레드에 keepalive 메시지를 일괄 게시하지 않는다. 최초 가져오기는 필요한
  메타데이터만 기록하며 과거 메시지 내용을 읽거나 요약하지 않는다.
- 전체 쓰레드 목록을 매일 완전하게 보고하지 않는다.
- Discord 검색, Hermes 세션 저장소, 일반 작업 관리자를 대체하지 않는다.
- 첫 버전에서 Discord 이외 채널까지 일반화하지 않는다.

## 첫 버전 완료 기준

- Hermes가 새로 만들거나 참여한 쓰레드는 수동 입력 없이 인벤토리에 들어간다.
- 사용자 상호작용이 없는 쓰레드도 지정 채널의 제한된 목록에 들어올 수 있다.
- 확인 뒤 새 Hermes 활동이 생긴 쓰레드는 다시 후보가 되고, 종료된 쓰레드는
  수동 재개 전까지 후보가 되지 않는다.
- 권한 있는 사용자가 확인·종료·재알림 상태를 바꿀 수 있다.
- 기록은 게이트웨이 재시작 뒤에도 남는다.
- 일반 메시지는 기존 Hermes 경로로 그대로 처리된다.
- 권한 없는 사용자는 장부를 변경할 수 없다.
- 유효하거나 인자는 잘못된 것으로 인식된 제어 명령은 모델 요청과 에이전트 답변을
  만들지 않는다. 플러그인의 고정 확인 메시지는 허용한다.
- 하나의 쓰레드가 자동 발견과 재알림에 동시에 해당해도 다이제스트에는 중복
  링크가 생기지 않는다.
- 기존 참여 쓰레드를 멱등하게 모두 등록하고, 새 자동 발견 후보가 과거 backlog에
  밀리지 않으며, 최초 결과 요약을 지정 채널에서 확인할 수 있다.
- 전송 실패 뒤 재시작해도 전달 의무를 잃지 않고, 같은 제어 명령의 상태 변경이나
  최초 가져오기를 중복 실행하지 않는다.
- reaction과 재시도 표식만으로 명령 적용 여부와 같은 날짜의 다이제스트 중복
  가능성을 구분할 수 있다.
- 각 다이제스트 항목에서 미확인·새 활동·과거·보관 임박·재알림 이유와 필요한
  시각을 확인할 수 있고, 같은 쓰레드는 한 번만 링크된다.
- 재시작이나 뒤늦은 Discord 히스토리 복구 뒤에도 이미 처리한 제어 명령 원문과
  플러그인의 고정 확인 메시지가 Hermes 세션·LLM 문맥에 들어가지 않는다.
- 잘못된 명령, DB 실패, 중복 실행, 에이전트가 바쁜 동안의 큐 처리를 검증한다.
